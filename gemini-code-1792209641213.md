# Backend Architecture Components: Controllers, Services, Repositories, Middlewares, and Request Context

## 1. The Backend Architecture Pattern
When a client sends an HTTP request to a server, separating the server's code into distinct components (Controllers, Services, and Repositories) is a vital design pattern. This separation of concerns makes the codebase scalable, maintainable, easier to debug, and easier to add new features.

---

## 2. The Controller (Handler) Layer
The Controller (or Handler) is the entry point for an API route after the routing algorithm matches the URL. Its primary responsibility is managing the flow of data from the client to the server, and back to the client.

### Step-by-Step Workflow of a Controller:
1. **Data Extraction:** The controller receives the HTTP request and response objects from the underlying programming runtime, extracting necessary data (e.g., query parameters for a GET request, or the JSON body for a POST request).
2. **Binding (Deserialization):** Deserializes the incoming JSON string into the programming language's native data format (like a Go struct, a Python dictionary, or a JavaScript object). If this fails, it halts and returns a `400 Bad Request`.
3. **Validation:** Checks if the incoming data matches the expected format, ensures mandatory fields are present, and prevents malicious payloads.
4. **Transformation:** Modifies data for backend convenience before passing it downstream (e.g., injecting default values for optional query parameters).
5. **Delegation:** Passes this clean, validated data to the Service Layer.
6. **Sending the Response:** Once the Service layer finishes processing, the Controller decides on the appropriate HTTP status code (`200 Success`, `201 Created`, `400`, `500`, etc.) and sends the final response back to the client.

---

## 3. The Service Layer
The Service Layer is where the actual business logic and core processing of the API happens.
* **Complete HTTP Isolation:** The Service layer should know absolutely nothing about HTTP. It does not deal with request/response objects, status codes, or validations. It acts as a standard function taking data in, processing it, and returning a result.
* **Orchestration:** A single service method can orchestrate multiple repository calls, merge data sets, send emails, or make external API calls.

---

## 4. The Repository (Database) Layer
The Repository layer's sole responsibility is dealing with database operations.
* **Workflow:** It takes data from the Service layer, constructs specific database queries (for inserting, filtering, or sorting), and returns raw database results back to the Service layer.
* **Single Responsibility Principle:** A repository method should only do one specific thing and return one type of data. Avoid complex conditional logic inside a repository; instead, create distinct methods for distinct data needs.

---

## 5. Middlewares
Middlewares are functions that execute in the middle of the request lifecycle—between the moment the server receives the request and the moment it hits the final Controller. 
* **Why use Middlewares?:** To centralize common operations (security, logging, parsing) and avoid duplicating code across hundreds of endpoints.
* **The `next()` Function:** Middlewares receive request/response objects and a `next` function. Calling `next()` passes execution to the subsequent middleware or handler. Alternatively, a middleware can return a response directly, terminating the request early.
* **Execution Order Matters:** Requests flow through middlewares sequentially.

### Common Examples of Middlewares:
* **CORS & Security Headers:** Placed early to check the origin; blocks unauthorized requests instantly.
* **Rate Limiting:** Checks IP addresses to prevent spam, returning a `429 Too Many Requests` error if limits are exceeded.
* **Authentication:** Verifies tokens. If invalid, returns `401 Unauthorized`; if valid, extracts user data and passes it downstream.
* **Logging:** Records request details (URL path, method, parameters) for debugging.
* **Global Error Handling:** Placed at the end of the chain to catch unstructured errors from controllers or services and format clean error responses.

---

## 6. Request Context
Request Context is a shared storage mechanism (usually a key-value store) strictly scoped to a single HTTP request.
* **Purpose:** Allows isolated function boundaries (middlewares and controllers) to share state and data without tightly coupling system code.

### Common Use Cases for Request Context:
1. **Passing Authentication Data:** Authentication middleware extracts `user_id` and role after token validation, saving them in the Request Context. The Controller pulls `user_id` directly from the Context to prevent spoofing.
2. **Request Tracing:** An early middleware generates a unique ID (UUID) and saves it to the Context, attaching it across microservices and logs to trace bugs.
3. **Cancellations:** Stores abort signals and timeout deadlines to prevent external service calls from hanging perpetually.
